Everyone can bolt a chatbot onto a banking portal. The hard part is letting it change something — a card block, a spending limit — without ever letting it change the wrong something.

We did not make the model more careful. We made it structurally unable to break the rules.

Where we start from

Today

  • Operators search customers and cards through dedicated portal widgets
  • Every widget calls the ESB directly, so the UI is welded to the API contract
  • Each card operation is a manual sequence: find, verify, act, record
  • Nothing links a request to what was done about it

With this solution

  • One sentence in plain language replaces the whole sequence
  • Consumers talk to an adapter, never to the API or the tables
  • Writes are proposed by AI, authorised by a human, executed deterministically
  • Every exchange is a case: who asked, what was done, how it ended
“The card ending 4417 was lost, block it.” one sentence; the agent finds it, checks its state, and asks you to approve

The agent cannot break the rules

Most agentic demos give the model direct table access. We deliberately did not: every tool calls our business layer, which re-validates everything and refuses what is invalid.

Direct table access
  • Model could block a cancelled card
  • Could set a daily limit above the monthly one
  • Could edit a transaction amount
  • Could read another bank's data
Through our business layer
  • State transitions validated: a permanent block is final
  • Limit hierarchy enforced: single, daily, monthly, credit
  • Transactions are read-only except the dispute flag
  • Bank perimeter applied at the data layer, fail-closed

AI proposes. A human authorises.

1
Understand The agent resolves the customer, the card, and its current state
2
Propose It parks a structured payload on the case. Nothing has changed yet
Authorise The operator sees the exact values and approves or rejects
3
Execute The approved payload runs deterministically. No model involved
What executes is exactly what was approved. It is never re-derived from the conversation, so a model that changes its mind between proposal and approval cannot alter the action.

Built for the ESB from day one

The MVP stores working data in local tables. Production will read the Digital Banking ESB. That switch was designed for before a single table existed.

Never changes
  • Portal widget
  • AI agents and their tools
  • Business operations and validations
  • Approval and audit trail
Swaps out
  • Local MVP tables
  • REST calls to the ESB
One adapter. One file.
Business keys, never sys_id
Everything is addressed by customer, card and transaction identifiers that still exist when the data comes from an API.
DTOs, never GlideRecord
The adapter returns plain objects already shaped like a REST payload. A GlideRecord would weld every caller to the table.
No card number, anywhere
Cards are identified by a tokenised id plus the last four digits. A full card number cannot be stored, requested, or reconstructed.
